**Post status flow for announcements:**
```
draft → pending_payment → active → expired
```

Non-announcement posts remain `active` immediately on creation as before. Add this status to the existing `Post` type.

**New Firestore collection:**
```ts
// announcement_payments/{paymentId}
type AnnouncementPayment = {
  id: string
  postId: string
  payerId: string
  payerPhone: string
  amount: number
  currency: 'UGX'
  iotecExternalId: string      // your unique ref sent to iotec
  iotecRequestId: string | null // returned by iotec after initiating collect
  method: 'mtn_momo' | 'airtel_money'
  status: 'pending' | 'confirmed' | 'failed'
  createdAt: Timestamp
  confirmedAt: Timestamp | null
}
```

**Payment flow — client side:**

Build `/screens/payments/AnnouncementPaymentScreen.tsx`:

- Display announcement preview (description truncated), amount due (UGX 5,000), and a note that a push prompt will appear on their phone
- Single input: confirm or pre-fill the phone number to charge (pre-fill from user's stored `whatsappNumber`, allow editing)
- Two buttons: **MTN Mobile Money** and **Airtel Money** — tapping either initiates the payment
- On button tap:
  1. Generate a unique `externalId` — format: `kisekka_{userId}_{timestamp}`
  2. Call iotec token endpoint to get access token:
     ```
     POST https://id.iotec.io/connect/token
     Content-Type: application/x-www-form-urlencoded
     client_id, client_secret, grant_type=client_credentials
     ```
  3. Call iotec collect endpoint:
     ```
     POST https://pay.iotec.io/api/collections/collect
     Authorization: Bearer {token}
     {
       amount: 5000,
       currency: "UGX",
       phoneNumber: "{user phone in 2567XXXXXXXX format}",
       category: "MobileMoney",
       externalId: "{generated externalId}",
       description: "Kisekka Online Announcement"
     }
     ```
  4. Write to Firestore `announcement_payments/{paymentId}`:
     - status: `pending`
     - store `iotecExternalId` and `iotecRequestId` from iotec response
  5. Update post status to `pending_payment`
  6. Navigate to `PaymentPendingScreen`

- Show loading state and disable buttons while the API call is in flight
- On API error: show toast with message, do not navigate away, allow retry

**Important:** The iotec `client_id` and `client_secret` are used here client-side for MVP. Add a clear `// TODO: move token generation to Cloud Function before production` comment. This is a known acceptable shortcut for MVP — we will fix it in a later phase.

**2. Cloud Function — iotec Webhook Receiver**

Create a Firebase Cloud Function in `/functions/src/index.ts`:

```ts
export const iotecWebhook = functions.https.onRequest(async (req, res) => {
  // 1. Accept POST only
  // 2. Parse the transaction object from req.body
  // 3. Extract externalId and status from the payload
  // 4. Query Firestore: find announcement_payment where iotecExternalId == externalId
  // 5. If status === 'Success':
  //      - Update payment document: status = 'confirmed', confirmedAt = now
  //      - Update linked post document: status = 'active'
  // 6. If status === 'Failed':
  //      - Update payment document: status = 'failed'
  //      - Update linked post document: status = 'draft'
  // 7. Respond 200 OK immediately regardless — iotec expects a fast response
})
```

- Deploy to Firebase Functions
- The deployed webhook URL goes into the iotec Pay portal under Wallet Details > Settings > Callback URLs
- Add the webhook URL to your `.env` as `IOTEC_WEBHOOK_URL` for documentation purposes

**Firestore Security Rules addition:**
```
announcement_payments/{paymentId}
  — read: owner (payerId == request.auth.uid)
  — create: authenticated, payerId must equal request.auth.uid
  — update: owner only from client. Cloud Function uses Admin SDK (bypasses rules)
```

**3. Push Notifications**

Use `expo-notifications` for all notification delivery.

**Setup:**
- Request notification permissions on first app open after onboarding completes — not during onboarding
- Store Expo push token on user Firestore document: `users/{userId}.expoPushToken`
- Create `services/notifications.ts` to handle token registration and permission requests

**Notification triggers — all client-side for MVP:**

| Trigger | Recipient | Message |
|---|---|---|
| Someone follows you | Followee | "{shopName} started following you" |
| New post by followed account | Follower | "{shopName} just posted: {description, 50 chars max}" |
| Announcement payment confirmed | Payer | "Your announcement is now live! 🎉" |

**Sending notifications:**
- After writing a follow document: read target user's `expoPushToken`, send via Expo Push API:
  ```
  POST https://exp.host/--/expoapi/v2/push/send
  { to, title, body, data: { type: 'follow', userId } }
  ```
- After creating a post: fetch `expoPushToken` of all followers, batch send via Expo Push API. Cap at 50 followers per post silently
- Payment confirmed notification is sent from the Cloud Function after updating post status to `active` — read payer's `expoPushToken` from Firestore and send via Expo Push API using Admin SDK

**Notification handling:**
- Foreground: show in-app `ToastNotification` component
- Background/killed: standard system notification
- Tapping a follow notification → navigate to that user's `ProfileScreen`
- Tapping a post notification → navigate to `PostDetailScreen`
- Set up notification response handler in root layout for deep link navigation
